# zooid relay engine

zooid is a multi-tenant Nostr relay built on [Khatru](https://gitworkshop.dev/fiatjaf.com/nostrlib/tree/master/khatru), pairing with the [Flotilla](https://flotilla.social) client as a NIP-29 community relay. The whole backend lives in the single Go package `zooid/` (module `zooid`, Go 1.25); `cmd/relay`, `cmd/import`, `cmd/export` are thin binaries over it. `README.md` is the user-facing config reference (every TOML field/env var); this skill is the code-level map of *how* those features are actually implemented, including where the implementation and the README diverge.

One thing to internalize before touching anything: **"multi-tenant" here means every virtual relay is a config file, not a database.** There is exactly one `*sql.DB` for the whole process (`database.go`, a `sync.Once`-guarded global), and tenants are isolated purely by SQL table-name prefix (`Schema.Prefix(table)` = `"{schema}__{table}"`, `schema.go`). The schema name is validated as a safe SQL identifier in exactly one place (`Config.Validate()`'s regex) and then spliced unparameterized into raw `CREATE TABLE` strings via `text/template` — safe today only because every real construction path goes through that one regex first. Full detail: [references/config-and-instance.md](references/config-and-instance.md), [references/event-store.md](references/event-store.md).

## The dispatch model and hot reload

`lib.go`'s `Start()` scans `Env("CONFIG")` once at boot, calls `MakeInstance(filename)` per file, and populates two maps — `instancesByHost` (keyed by the config's `host`) and `instancesByName` (keyed by filename) — behind `instancesMux sync.RWMutex`. `cmd/relay/main.go`'s HTTP handler resolves every incoming request via `zooid.Dispatch(r.Host)`. An `fsnotify` watcher on the config directory then hot-loads/reloads/unloads instances as files change.

**The reload path always tears down the existing instance before rebuilding it** (`lib.go:102-152`) — if the rebuild fails (transient parse error from a non-atomic `Config.Save()` write, or a hand-edited config that now fails validation), the relay is left **absent from both maps with no rollback or retry** until another filesystem event happens to parse successfully. There is no "keep serving the last-good config" behavior. Relatedly, `Instance.Cleanup()` only stops the per-instance hourly expiration-manager goroutine (`EventStore.Close()` is a deliberate no-op, since the DB is shared) — skip calling it when discarding an `Instance` and that goroutine leaks indefinitely, keeping the whole object graph reachable. Duplicate `host`/`schema` across config files dropped directly on disk (bypassing the REST API) is **never** checked by `lib.go`/`config.go` — only `api.go`'s REST handlers check it. Full detail: [references/config-and-instance.md](references/config-and-instance.md) §6.

## Config: one struct, TOML and JSON both

`Config` (`config.go:14-80`) is decoded from TOML (config files) or JSON (`api.go`'s REST body) into the identical struct, and both loaders call the same `Config.Validate()` before returning. `Validate()` does more than validate — it also **defaults** `Blossom.Adapter` to `"local"` and **caches** the parsed secret key (`config.secret`), so any hand-built `Config{}` literal (as every `_test.go` file does) that skips `Validate()` will have a broken `Sign()`/`GetSelf()`/`IsSelf()`.

The roles model has one very non-obvious rule: a role table literally named `[roles.member]` applies to **every pubkey unconditionally** — its own `pubkeys` list is never consulted (`Config.GetAllRoles`, `config.go:233-244`). `CanInvite`/`CanManage` are additive across every role a pubkey matches (never restrictive), and both always return `true` for the relay's own signing identity (`IsSelf`) and the NIP-11 owner pubkey (`IsOwner`), independent of relay membership. Role *pubkeys* are never format-validated — a typo in `[roles.admin].pubkeys` silently grants nothing, with zero feedback anywhere. Full detail: [references/config-and-instance.md](references/config-and-instance.md) §5.

## Storage: EventStore over raw SQL

`EventStore` (`events.go`) implements Khatru's `eventstore.Store` over two tables per tenant (`{schema}__events`, `{schema}__event_tags`), with only single-letter tag keys indexed (the NIP-01/12 `#<letter>` convention — multi-letter tags live only in a JSON blob and are never filterable at the SQL layer). An architecture audit turned up several real, now-fixed bugs here that are worth knowing about because they explain non-obvious shapes in the current code:

- **Full-text search requires the `sqlite_fts5` build tag.** `justfile`'s `run`/`build*`/`test` recipes all pass `-tags sqlite_fts5` for exactly this reason — build or test this package without it (e.g. a bare `go build ./...`) and `EventStore.Init()` will silently disable search (`FTSAvailable = false`) because `mattn/go-sqlite3` doesn't compile in the fts5 SQLite extension otherwise. (There used to be a second, independent bug on top of this — the fts5 schema string wasn't passed through `Schema.Render`, so even with the tag it would have failed to create — that's fixed; `Init()` now also runs an fts5 `'rebuild'` command every startup so events written before either fix still become searchable.)
- **`QueryEvents(filter, maxLimit)` now actually caps a filter with `Limit == 0`** (the normal "no limit specified" case), not just one that already specified a larger limit. `instance.QueryStored`'s 1000-row cap on ordinary requests is real again.
- **`SaveEvent`/`ReplaceEvent` run inside a transaction**, retried from scratch (fresh `BEGIN`, not just a wait) on `SQLITE_BUSY`/`SQLITE_BUSY_SNAPSHOT` via the shared `runInTx` helper — necessary because SQLite only allows one writer at a time and a snapshot going stale mid-transaction under WAL mode isn't something waiting longer fixes, only restarting the transaction is. `saveEvent` detects duplicates via the primary key constraint itself (`isUniqueConstraintErr`) rather than a separate existence check, so there's no check-then-insert window for a concurrent save of the same event to race through.
- **`CountEvents` no longer double-applies the filter's `Limit`** inside its own `COUNT(*)` subquery — a `Limit` is a delivery hint for `QueryEvents`, not a count cap.

`ReplaceEvent` deliberately does **not** follow NIP-01's tie-break recommendation (lowest id wins on an exact `created_at` tie) — it keeps "whichever update was processed last," full stop. This isn't an oversight: zooid uses replaceable/addressable kinds as its own internal, single-writer state store (banned lists, member lists, role assignments, group pins, ...), where two updates landing in the same wall-clock second are routine, and an admin action must never be silently discarded because of how its event id happens to hash. (An earlier attempt to "fix" this into spec-compliant lowest-id-wins behavior broke `TestGroupStore_UpdatePins`, `TestManagementStore_AllowPubkey`/`UnbanPubkey`/`AssignAndUnassignRole` — a genuine case where matching the external protocol spec would actively regress this codebase's own usage.)

`Instance.GenerateInviteEvent` (`instance.go:208-234`) is fixed too: its existence-check filter used tag key `"#p"` instead of the bare `"p"` every other call site in this codebase uses, so the filter was silently dropped by the single-letter-key check and the function could return a *different pubkey's* invite/claim event. Full detail, plus the full table/index/query-builder shape: [references/event-store.md](references/event-store.md).

## Authorization: four systems that share vocabulary, not implementation

Before adding or changing anything permission-related, know that this codebase has **four distinct authorization concepts**, and conflating them is the easiest way to introduce a bug:

1. **Config-driven static roles** (`[roles.*]` in TOML) — deploy-time, not an event.
2. **Relay-wide dynamic membership** (`ManagementStore`, backed by a replaceable `RELAY_MEMBERS`(13534) event plus an append-only `RELAY_ADD_MEMBER`/`RELAY_REMOVE_MEMBER` audit trail). `GetAdmins()` is **not** derived from this — admin status is 100% config-driven (owner + `CanManage` roles).
3. **Dynamic role labels** (`RELAY_ROLE`(33534), NIP-86 `createrole`/`assignrole`) — purely cosmetic UI metadata (label/color/order for Flotilla). **`AssignRole` grants zero permissions** — it's never consulted by `CanInvite`/`CanManage`/`IsAdmin` anywhere.
4. **Per-group NIP-29 membership** (`GroupStore`, standard `h`-scoped put/remove-user events). `GroupStore.IsAdmin(h, ...)`/`GetAdmins(h)` **ignore `h` entirely** and delegate to the same global relay admin set — there is no such thing as a per-group admin distinct from the relay-wide one.

The Khatru policy hooks in `instance.go` (`OnConnect`, `OnRequest`, `QueryStored`, `OnEvent`, `PreventBroadcast`) compose these plus the `[policy]` config flags (`public_read`/`public_write`/`public_join`/`strip_signatures`) in a specific, load-bearing order — e.g. `PreventBroadcast`'s fallback path never re-checks ban status for non-group events, so an already-open subscription from a since-banned pubkey keeps receiving ordinary broadcasts until it reconnects. Invite/claim codes (kind 28935) are **reusable by design** (redemption never consumes them) and are one of the only ephemeral-kind-range events (20000–29999) that zooid deliberately persists server-side, bypassing Khatru's normal ephemeral fast-path. Full detail, including the exact NIP-86 method dispatch table and the ban-list mechanics: [references/groups-and-management.md](references/groups-and-management.md).

## The REST management API and integrations

`api.go` is a separate JSON REST API (not the Nostr relay protocol) for remotely managing virtual relay *configs*, gated by `API_HOST`/`API_WHITELIST` and NIP-98 HTTP auth. `validateNIP98Auth` (`util.go`) enforces a ±60s window on the auth event's `created_at` — without this a captured `Authorization: Nostr ...` header would be replayable forever; this check is shared by the LiveKit token endpoint too. `PATCH /relay/{id}` implements RFC 7396 JSON Merge Patch semantics (`null` deletes a field, objects merge recursively, everything else replaces wholesale) via a hand-rolled `deepMerge`. Duplicate `host`/`schema` detection lives here, not in `config.go`, and silently skips any sibling config file that currently fails to parse.

`blossom.go`/`push.go`/`livekit.go` are optional feature integrations, each gated by its own `[section].enabled` config flag:

- **Blossom** media storage (local disk or S3, membership-gated, no per-group granularity). Two real bugs in the vendored `khatru/blossom` package — a nil-pointer panic in `handleDelete` on a missing/malformed `Authorization` header, and an SSRF hole in `handleMirror` (an unrestricted server-side `http.Get` of a client-supplied URL) — are fixed **directly in the `nostrlib` source** (a sibling checkout at `../nostrlib`, the same org's fork zooid's `go.mod` pins via a `replace` directive), not worked around in zooid. `blossom.go` itself is unmodified from a bare `blossom.New(...)` call plus the four `Reject*` hooks.
- A webhook-style **"NIP-9a" push** mechanism (relay POSTs to a client-registered HTTP callback on matching events). `ValidatePushSubscription` rejects an obviously-local callback URL at registration time, and — because a hostname can resolve differently later (DNS rebinding) — the `http.Client` built in `PushManager.Enable` also guards every actual dial via `net.Dialer.Control`, refusing to connect to loopback/private/link-local/unspecified/multicast addresses regardless of what the URL's hostname resolves to at delivery time. (The Blossom mirror SSRF above uses this exact same dial-guard technique, added to `nostrlib` directly.)
- **LiveKit** audio/video (one LiveKit room == one NIP-29 group; rooms are stamped with the owning relay's schema so a single shared `API_HOST` webhook endpoint can route to the correct tenant, verified safely because the per-tenant HMAC signature check happens *after* the schema-based routing).

The NIP-86 `listbannedevents` method also had a vendored-dependency dispatch bug — `khatru/nip86.go`'s dispatcher nil-checked `ManagementAPI.ListBannedEvents` but then actually called `ManagementAPI.ListEventsNeedingModeration`, panicking on a nil function value for any relay (like zooid) that only wires up `ListBannedEvents`. Fixed with a one-line change directly in `nostrlib` (the call now matches the nil-check); zooid's `management.go` has no workaround for this anymore. One side effect: `listeventsneedingmoderation` is a recognized NIP-86 method name (`nip86.DecodeRequest` knows it) but zooid never wires `ManagementAPI.ListEventsNeedingModeration`, so it now correctly answers `"method listeventsneedingmoderation not supported"` instead of silently succeeding as an alias for `listbannedevents` the way the old workaround made it behave. Full detail, and the general "fix upstream vs. work around" decision process, in [references/api-and-integrations.md](references/api-and-integrations.md).

## Where to make changes

- **A new config field** → add it to the right struct in `config.go`, add any required-ness/format check to `Config.Validate()` in the same order as neighboring checks, and update `README.md`'s matching section. If it's sensitive, remember the whole `Config` round-trips through the JSON API in cleartext with no redaction.
- **A new NIP-86 management method** → add a handler closure in `ManagementStore.Enable` (`management.go:693-788`), matching the `nip86.RelayManagementAPI` field name exactly (lower-cased field name = wire method name), gated by the same `CanManage` check every other method uses.
- **A new event kind constant** → add it to `lib.go`'s const block alongside the existing `RELAY_*`/`PUSH_SUBSCRIPTION` kinds, and add it to `IsInternalEvent`/`IsReadOnlyEvent`/`IsWriteOnlyEvent` in `util.go` if it needs special read/write visibility — these three predicates are what `OnEvent`/`QueryStored`/`PreventBroadcast` all key off of.
- **A new Khatru policy hook or write-path check** → goes in `instance.go`, in the same ordered chain as the existing checks in `OnRequest`/`OnEvent` — read `groups-and-management.md` §3 first, the ordering is load-bearing (e.g. ban checks are asymmetric between the public and private branches by design).
- **A new REST API endpoint** → register it in `NewAPIHandler` (`api.go:21-47`) wrapped in `api.auth(...)` unless it has its own independent auth (like the LiveKit webhook).
- **A new background/integration feature** (like push or LiveKit) → gate it behind its own `Config.<Section>.Enabled` flag, wire `Enable(instance *Instance)` from `makeInstance` the same way `Groups`/`Push`/`Management`/`Blossom` already do, and update `Relay.Info.SupportedNIPs` in the same place.

## Building and verifying a change

Per `justfile`: `just run` (go run), `just build-relay`/`build-import`/`build-export` (or `just build` for all three), `just test` (`go test -v ./...`), `just fmt` (`gofmt -w -s .`). **All of these require both `CGO_ENABLED=1`** (since `mattn/go-sqlite3` is cgo-based) **and `-tags sqlite_fts5`** (to actually compile in fts5 search support) — the justfile recipes already pass both; don't drop either if you invoke `go build`/`go test`/`go run` directly, or full-text search will silently disable itself and any FTS-dependent test will skip. Tests in this package share a single temp `DATA` dir per test binary run (`main_test.go`'s `TestMain`) and a memoized `Env()` (`env.go`, `sync.Once`) — `api_test.go` documents the resulting constraint explicitly: package tests must run **sequentially**, since `Env()` can't be re-initialized via `os.Setenv` mid-run (tests that need to control env vars mutate the package-level map directly instead). Don't introduce `t.Parallel()` in this package without accounting for that.

## House notes

- Nearly every shared resource in this package (`GetDb()`, `Env()`, `GetKeyValueStore()`) is a `sync.Once`-guarded package-level global — this is the established idiom here, not something to refactor away.
- Comments are sparse and mostly absent; where they exist they tend to explain a genuinely non-obvious *why* (e.g. `EventStore.Close()`'s "never close the database, since it's a shared resource"). Match that density rather than adding narrative comments to new code.
- The sharp edges catalogued in the references below (FTS5, the `maxLimit`/`CountEvents` bugs, the `"#p"`/`"p"` tag-key bug, the Blossom DELETE/mirror bugs, the `listbannedevents` panic, the NIP-98 replay window, push-callback SSRF) have all been fixed, with regression tests locking each one in (`events_test.go`, `instance_test.go`, `util_test.go`, `push_test.go`, `blossom_test.go`, `management_test.go`, plus `handlers_test.go`/`nip86_test.go` in `nostrlib/khatru`/`nostrlib/khatru/blossom`). They're kept documented here because the fixes explain otherwise-non-obvious shapes in the current code (the `runInTx` retry wrapper, the dial-time `net.Dialer.Control` hooks) — treat that shape as load-bearing, not incidental.
- **`fiatjaf.com/nostr` is replaced with a fork the same org maintains, and a local checkout of it lives at `../nostrlib`** (sibling to this repo, same remote as the `replace` directive in `go.mod` — `git -C ../nostrlib log --oneline -1` should match the pinned pseudo-version's commit hash). When a bug turns out to be in the vendored dependency rather than zooid's own code, prefer fixing it **there** and bumping zooid's `go.mod`/`go.sum` (`go mod edit -replace fiatjaf.com/nostr=gitea.coracle.social/Coracle/nostrlib@<new-pseudo-version>` after the fix is committed and pushed — a pseudo-version is only resolvable once the commit exists on the remote) over adding a local workaround in zooid. Every vendored-dependency bug found in the audit this skill documents (the Blossom DELETE/mirror bugs, the `listbannedevents` dispatch bug) ended up fixed exactly this way, once it was clear `../nostrlib` was available and in scope — a same-repo local workaround is the fallback for when patching upstream genuinely isn't practical or authorized, not the default. If you bump the dependency, re-check whether any zooid-side workaround for the same bug can now be deleted instead of left as redundant belt-and-suspenders (this happened twice already — the `blossom.go` DELETE guard and the `ListEventsNeedingModeration` aliasing were both removed once their upstream fixes landed).
